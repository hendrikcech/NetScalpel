NETSCALPEL STATIC UDP RATE INVESTIGATION
======================================

Scope
-----
Branch: investigate/udp-rate-stability. Sender/production code is unchanged.
New benchmark: e2e/udp_stability.py; usage: e2e/UDP_STABILITY.md.
This report records a single-host investigation, not a universal timing SLA.

Code review (no production changes)
-----------------------------------
1. Unlimited catch-up: pkg/udp.go:479-498,526-545,553-604 computes a
   cumulative packet goal and immediately drains the entire deficit, in batches
   up to 1024 packets. The nominal five-packet ticker interval is NOT a burst
   cap. At 500 nominal Mbps a 60ms interruption creates about 2678 packets of
   debt, allowing three back-to-back batches on resumption. This is a NetScalpel
   pacing-policy choice; a scheduler interruption need not originate in it.

2. Stale tick times: pkg/udp.go:526-527 uses the timestamp delivered by the Go
   ticker rather than current monotonic elapsed time. After delayed delivery,
   the first resumed iteration may use an old goal, delaying catch-up until a
   later tick. Using current elapsed time would remove that extra lag, but
   would NOT solve unlimited catch-up or provide real-time scheduling.

3. Accounting: cmd/scalpel-run/main.go:125-131 computes pps using 1400 bytes;
   pkg/common.go:63-69 adds an 8-byte sequence. Actual UDP payload = 1408.
   At nominal 500Mbps expected payload rate = 502.847488Mbps. The benchmark
   reports both; this constant discrepancy cannot explain a time-varying dip.

4. Measurement caveat: pkg/txtsreader.go:167-179 discards all kernel TX times
   on a count/size mismatch. Fallback timestamps in pkg/udp.go:562-579 are
   taken once per batch BEFORE encoding and sendmmsg, not at packet departure.
   Check logs before interpreting older CSV plots. Capture matching is needed
   to distinguish this from true egress bursts.

5. Defects found, not exercised as identified causes here:
   - pkg/udp.go:595-601 advances seq by the successful short-send count, then
     subtracts the unsent count again. Example: request100/send60 advances seq
     by20, not60; sequence reuse/underflow can corrupt result matching.
   - pkg/sockets.go:85-105,114-125 overwrites errors set in rawConn.Control's
     callback with Control's own return value, potentially hiding failed
     timestamp setup. TX also overwrites the setsockopt error with getsockopt.
   - pkg/udp.go:571-576 reuses the previous slice length when encoding; a later
     larger-payload segment can fail despite available buffer capacity. This
     does not affect the fixed-size CLI tests.

6. Optimization candidates, not proven root causes:
   - pkg/common.go:63-84 randomizes padding anew for every packet. Reusable
     incompressible buffers could remove substantial per-packet CPU work.
   - pkg/txtsreader.go:87-125 uses allocating/reflection-based ancillary-data
     decoding per packet; consider direct fixed-layout decoding and profiling.
   - pkg/txtsreader.go:34 starts timestamp storage at1024 and grows it during
     the run, alongside a separate sender-record stream. Preallocation avoids
     repeated large copies/GC pressure on long/high-rate runs.
   - Kernel pacing (e.g. suitably designed SO_TXTIME/FQ) or bounded catch-up
     deserves separate evaluation. A debt/burst cap trades cumulative count
     accuracy for short-window stability and needs an explicit policy decision.

Attribution limits
------------------
There is no code-defined 60ms ramp/stall. External scheduling, cgroup quota,
host/VM contention, GC, encoding work and socket backpressure are plausible
triggers, not interchangeable explanations. A controlled sender pause can prove
the catch-up response without proving the cause of an unexplained original dip.
Independent software capture matching rules out CSV-only timestamp artifacts
for the matched run, but does not establish physical NIC/wire timing. A remote
tap/receiver or hardware timestamps are needed for that stronger claim.

Measured results: private loopback
----------------------------------
2026-10-16; base revision cbe868c20a74aa6702ef2a38877b66ec8577f83a.
Normal Go 1.26.8 build, Linux 6.18.55, KVM guest exposing four i7-4770 CPUs.
tcpdump 4.99.6, 128-byte snapshots, 16 MiB capture buffer, nanosecond pcap.
Each profile ran sequentially, three 2-second transfers per listed rate.
An earlier exploratory sweep overlapping Go tests was NOT used in these numbers.

All 39 loopback captures matched every CSV sequence/size, had zero kernel
capture drops, and retained kernel TX timestamps (no userspace fallback).
Raw evidence: out/udp-stability-{clean,pinned,compete,pause60}/.
Those generated directories are gitignored; this report preserves key results.

At 500 Mbps: 70.15-73.85% of 1 ms bins were outliers; maximum interpacket gaps

The competitor is one continuously busy Python process on the same CPU. At 1 Gbps,
60 ms window rates in one run ranged 712.64-1179.15 Mbps, with a 34.1 ms cumulative
traffic deficit before catch-up. Whole-test mean still ~1005 Mbps. This shows
CPU availability matters much more at high rates; it does not identify a
universal hardware capacity threshold or reproduce a slower CPU's frequency.
Read local cgroup cpu.max was 'max 100000'; no local quota was configured.
Host-wide steal ticks were small, not correlated to individual outliers.

Deliberate external 60 ms SIGSTOP at 500 Mbps (three runs):
- Actual injected pause 60.25-60.32 ms, starting 114.0-122.6 ms after seq=0.
- Captured max gap 60.38-61.35 ms, followed by real over-goal transmission.
- Example: five successive zero-rate 10 ms bins, followed by 10 ms bins at
  1208.6, 1409.1, 1647.9 Mbps. Whole-test payload mean 502.72 Mbps.
- Example cumulative deficit reached 65.22 ms of target-rate traffic, then ended
  only 0.493 ms behind. This reproduces the deficit/catch-up SHAPE with a known
  external trigger; it is not an unexplained spontaneous 60 ms startup ramp.

Capture-vs-reporting evidence:
Across all 39 runs, per-run median(capture minus CSV TX) was 0.218-4.140 us.
Largest deviation from its run median was 145.443 us, not tens of milliseconds.
Common-origin 10 ms capture and CSV rates differed by at most 1.126 Mbps (one
1408-byte packet crossing a window boundary). The large stalls/bursts above
therefore occurred in actual kernel-observed packet transmission, not merely
CSV send-timestamp reporting. Physical-wire timing remains untested.

Capture overhead control
------------------------
Six additional standalone transfers ran without tcpdump, otherwise using the
same Go 1.26.8 binary, private loopback and 2-second duration. CSV retained kernel
TX timestamps in all six; these controls are NOT independent capture evidence.
At 500 Mbps, CSV 10 ms outliers were 9.5-11.0%; at 1000 Mbps, 8.5-11.5%.
All 60 ms windows were within tolerance. These distributions overlap the
capture-on baseline, so capture overhead is not needed to explain the observed
jitter. Small non-interleaved samples cannot exclude a subtler observer effect.
Evidence and exact CLI commands: out/udp-stability-capture-off/summary.json.

- 'go test ./...' failed only TestTCPDLBBR: this kernel has no BBR support.

Conclusion
-----------------
Yes: short-window jitter and deficit/catch-up overshoot are reproducible.
No: a spontaneous ~60 ms settling deficit at 500 Mbps is not established here.
Both layers matter: external CPU/scheduling delays can cause deficits, while
NetScalpel's unlimited repayment policy turns them into overshoot. Code review
also identifies avoidable CPU/allocation work and independent correctness bugs.
The precise cause on the original sender still requires running the benchmark
there and correlating timing with quota/scheduler/GC/backpressure evidence.
